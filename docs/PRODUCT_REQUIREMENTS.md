## Purpose

Improve conditional discovery of all-ages TRPG scenarios on BOOTH. Purchase, payment, and download remain on BOOTH; this application only assists in finding scenarios.

---

## Discovery Goals

- Reduce over-concentration on popular items in search results.
- Enable discovery of scenarios for unfamiliar or lesser-known TRPG systems.
- Allow users to find scenarios by player count and play time.

---

## MVP Source and Scope

- **Source**: BOOTH only.
- **Content**: All-ages TRPG scenarios across all systems.
- **Extensibility**: Architecture supports future product-type extension (e.g., supplements, GM screens) without requiring a full rewrite.

---

## MVP Exclusions

The following are explicitly excluded from the MVP:

| Excluded item | Note |
|---|---|
| R-18 and R-18G content | Excluded from collection, storage, and publication |
| User accounts and login | No authentication in MVP |
| Favorites / personal lists | No per-user state |
| Internal product-detail pages | Navigation goes to BOOTH; no internal detail pages |
| Product images | Not collected or displayed |
| Exact prices | Not collected or displayed |
| Advertising | No ad integration |
| Affiliate links | No affiliate integration |
| Author submission | No author-side content submission |

---

## Navigation

Search results link directly to the parent BOOTH product page. There are no internal product-detail pages in the MVP.

---

## Sales-State Handling

- Products with ended sales status are excluded from normal search results.
- Ended-product records are retained in internal history for data continuity and reconciliation.

---

## Player Count (PL) Rules

- Each scenario records a **minimum** and **maximum** player count (PL).
- Separate fields for:
  - **GM/KP required** — a dedicated game master or keeper is required.
  - **GM-less** — the scenario runs without a dedicated GM.
  - **KPC** — a keeper player character role exists.
- Unknown values are stored explicitly as unknown, not as zero or null.

---

## Play-Time Rules

- Each scenario records a **minimum** and **maximum** play time.
- Modality-specific time is recorded separately when a scenario has distinct online/offline durations.
- Explicit **unknown** handling: unknown play time is stored as unknown, not inferred or omitted.

---

## Additional Scenario Fields

The following are recorded as separate fields (not folded into tags or description):

| Field | Description |
|---|---|
| Conversation method | How players communicate (e.g., text, voice) |
| Play environment | Where the scenario is played (e.g., online, offline, VR) |
| Progression method | How the scenario advances (e.g., branching, linear) |
| Work composition | Single scenario, collection, series, etc. |
| Handout | Whether handouts are included and their type |

## Tag System

### Five Initial Tag Categories

1. **Theme** — narrative or genre themes
2. **Tone** — emotional or tonal qualities
3. **Content warning** — potentially sensitive content flags
4. **Mechanic** — special mechanical rules or requirements
5. **Setting** — world or setting descriptors

### Provenance

Tags are separated by provenance:

- **Source tags**: extracted directly from BOOTH product data.
- **Derived tags**: generated by rules or AI from product content.

### Derived-Tag Evidence Metadata

Each derived tag records:
- source evidence (which content it was derived from)
- confidence level
- conflict flags if multiple sources disagree

### Spoiler Exclusions

Tags that would reveal plot spoilers are excluded from public display. Spoiler-suspect AI output is not automatically published (see [DATA_COLLECTION_POLICY.md](DATA_COLLECTION_POLICY.md)).

## System and Rulebook Structure

- **Normalized system field**: TRPG system is stored in a normalized form.
- **Edition**: Each system entry records the specific edition when relevant.
- **Aliases**: System aliases and alternate names are stored to support search.
- **Required rulebooks**: Rulebooks required to play are recorded.
- **Optional rulebooks**: Rulebooks that are useful but not required are recorded.
- **Supplements**: Relevant supplements are recorded separately from core rulebooks.

---

## Two-Layer Product/Scenario Model

### Layer 1: BOOTH Product

A single record per BOOTH product page. Contains BOOTH-level metadata such as product URL, title, creator, and sales state.

### Layer 2: Individual Scenario

One or more scenario records linked to a BOOTH product. Scenarios carry the playable-content fields (PL, play time, system, tags, etc.).

### Scenario Collections

A single BOOTH product may contain multiple scenarios. Conservative handling applies:
- Each scenario in a collection is modelled as a separate scenario record.
- When individual scenario metadata cannot be reliably separated, the collection is held pending manual review rather than published with inferred data.

### Excluded Items

Products that contain only materials (supplements, GM screens, maps) or DLC with no standalone playable scenario are excluded from scenario search results. They may still be retained as BOOTH-product records for reference.

## Design Direction

- **VRCFinder**: Treated as a structural reference only (search interaction patterns, faceted filtering). VRCFinder's visual design is not adopted.
- **Retro Japanese archive-room design**: The distinct visual direction for this application. Evokes the aesthetic of a physical archive or storeroom, not a modern SaaS product.

---

## Language and Accessibility

- **Language**: Japanese-only MVP. Internationalization is out of scope for MVP.
- **Accessibility**: Modern accessibility requirements apply:
  - Keyboard navigation for all interactive elements.
  - Mobile-responsive layout.
  - Performance: pages must load within acceptable limits on mobile connections.
  - No blinking or flashing content.
